# 修复消息已读状态无法写入数据库的问题

## 问题分析

消息查阅后又显示未读，主要原因是：
1. `system_messages_status` 表缺少 `INSERT` 权限的 RLS 策略
2. 当用户首次查看消息时，无法向 `system_messages_status` 表插入新记录
3. 虽然有 `UPDATE` 权限策略，但没有 `INSERT` 权限策略，导致首次阅读时状态无法持久化

## 修复方案

### 1. 数据库层面修复

**执行现有的修复 SQL 文件**，为 `system_messages_status` 表添加正确的 `INSERT` 权限 RLS 策略：

```bash
# 执行修复文件
supabase migration new fix_message_status_rls
# 或者直接在 Supabase 控制台执行 fix_message_status_rls.sql 中的 SQL 语句
```

### 2. 应用代码层面修复

**修改 `markAsRead` 函数**，使用 `upsert` 操作代替当前的先检查后插入/更新逻辑：

1. 在 `MessageCenterScreen.tsx` 中，将 `markAsRead` 函数修改为使用 `upsert` 操作
2. 确保无论记录是否存在，都能正确标记消息为已读
3. 简化代码逻辑，提高性能

### 3. 修复后的 `markAsRead` 函数示例

```typescript
const markAsRead = async (messageId: string) => {
  try {
    if (!userInfo || !userInfo.id || !supabase) {
      return;
    }

    // 使用 upsert 操作，无论记录是否存在都能正确更新
    const { error } = await supabase
      .from('system_messages_status')
      .upsert(
        {
          message_id: messageId,
          user_id: userInfo.id,
          is_read: true,
          read_at: new Date().toISOString()
        },
        {
          onConflict: 'message_id,user_id' // 指定唯一约束
        }
      );

    if (error) {
      console.error('标记消息为已读失败:', error);
      return;
    }

    // 更新本地状态
    setMessages(prev => prev.map(msg => 
      msg.id === messageId ? { ...msg, is_read: true } : msg
    ));
  } catch (error) {
    console.error('标记消息为已读异常:', error);
  }
};
```

## 验证方案

1. **本地测试**：运行应用，查看消息，验证已读状态是否正确保存
2. **数据库验证**：检查 `system_messages_status` 表中是否有新的记录插入
3. **重新启动应用**：验证消息已读状态是否持久化

## 预期效果

- 消息查阅后，已读状态正确写入 `system_messages_status` 表
- 重新打开应用或消息中心，消息保持已读状态
- 提高消息状态更新的性能和可靠性

## 风险评估

- 低风险：使用 `upsert` 操作是安全的，不会破坏现有数据
- 兼容性：`upsert` 是 Supabase 支持的标准操作
- 性能：减少了数据库请求次数，提高了性能
